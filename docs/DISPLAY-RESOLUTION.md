# 3.2K 面板能不能"降分辨率"

问题（2026-11-05，用户）：*平板的真实分辨率是 3.2K，SoC 带这块屏有点吃力，能不能在编译过程中降一下？*

**一句话**：编译期没有这个开关——面板时序是固件的事；但"渲染分辨率"确实能降，机制是
**DPU 的 VIG 缩放器（QSEED）**把 1600×1068 的合成器帧 1:2 放大到 3200×2136 扫出。
代价约 150 行寄存器编程，收益是合成器像素降到 1/4。它**不是**现在的瓶颈，排在 DPU 直扫之后。

## 1. 为什么"编译期"这条路不通

| 层 | 谁定的 | 能不能在构建里改 |
| --- | --- | --- |
| 面板时序（HSYNC/VSYNC/ACTIVE/PHY/DSI 双链路） | ABL 从 DT 的面板节点配置，固件已点屏 | ❌ uke 的 DPU 线把"不改 INTF/PHY 时序"当铁律（`DPU-TASKS.md` §8.3），改错就是黑屏 |
| 固件 GOP 几何（我们拿到的 `Video[0]`） | UEFI（Mu-Silicium）按面板分辨率建 GOP；DTB `splash_region` 给的是同一块 | ⚠️ 改小 `splash_region` 只会让画面缩在左上角：DPU 仍按 3200×2136 扫 |
| 合成器出帧尺寸 | 显示驱动报给 iPadOS 的模式 | ✅ **这一层才是能降的**，但要让 DPU 放大才不会缩成一角 |

所以"编译时改个数字"降不了；能降的是**渲染**，而且降了必须补一个放大环节。

## 2. 数字

| 项 | 3200×2136（现在） | 1600×1068（1/2 × 1/2） |
| --- | --- | --- |
| 像素/帧 | 6,835,200 | 1,708,800（¼） |
| BGRA 字节/帧 | 27,340,800（27.34 MB） | 6,835,200（6.84 MB） |
| scanout 带宽 @60 Hz | 1.64 GB/s | 0.41 GB/s |
| scanout 带宽 @120 Hz | 3.28 GB/s | 0.82 GB/s |
| 合成器每帧 GPU 工作量 | 6.68 Mpx、32 draw、1.65 全屏 pass | ≈ 1/4 |

以上是 uke 在 `DPU-PORT.md` §8.4 里量出来的同一块面板（cliffs + O82 3200×2136）的数。

## 3. 但现在它不是瓶颈（uke 的实测，比推断可靠）

30 fps 那一版的账（`DPU-TASKS.md` §17、§24）：

- CPU 不是瓶颈：d0 4×A520 = 1593 MHz，d1 A720 = **2611 MHz（满）**，d2 X4 = **2803 MHz（满）**。
- GPU 没降频：`UKE GPU: revote` 被接受，`X v0/0`，950 MHz 顶档。
- 每帧成本在合成器自己：1 pass / 32 draw / 6.68 Mpx，`commit-to-complete` 27–41 ms。
- 大头是 GPU↔主机内存带宽：`B fill=1758MB/s copy=3745MB/s`，每帧约 67 MB 阴影回拷 ≈ 18 ms。
- 横向对照 sheng：**3048×2032（只比我们少约 10% 像素）、同一个 0x130000000 VM、90–120 fps**。
  差异是 GPU 档位（A740 vs A732）、DCVS 和 scanout 实现，不是像素数。

结论：像素数是**下一个** 4 倍，不是**这个** 4 倍。现在最该动的是 GPU 合成器与显示直扫
（见 `docs/GPU-UKE-ALIGNMENT.md` 与 uke 的 `DPU-PORT.md` §8），降分辨率排在它们后面。

## 4. 真要做的话，路径是这样

1. **前提**：先有 DPU 直扫（uke 的 D1b/D2：`presentBase` 把 surface 页映射进 stage-1 窗口，
   直接 flip VIG0/VIG1）。在现在的 CPU 拷贝路径上降分辨率没有意义——拷多少像素都不是瓶颈，
   而且仍要把整屏 27 MB 写一遍。
2. **报小模式**：显示驱动按 1600×1068 报模式，`/chosen` 的 `display-scale=1`
   （`package/LegacyDisplayProbe.cpp` 的 `offline-legacy-unit-scale` 已经是这个旋钮的位置）。
   这样 UI 的逻辑布局与 3200×2136 时**一样**，只是每个逻辑点占 1 个物理像素而不是 2 个。
3. **VIG 放大**：给 VIG0/VIG1 各写一次 scaler——`SRC_SIZE`/`out_size` + QSEED 的相位步进
   （stock 参考全部在 `drivers/gpu/drm/msm/disp/dpu1/dpu_hw_sspp.c: setup_scaler` 与
   `dpu_hw_sspp_scaler.c`，SM7675 原厂内核里就有）。
4. **验收**：三图案（纯色/棋盘/渐变）色位正确；`CTL_FLUSH` latch < 8.3 ms；UI 是"软"而不是"缩"
   ——把桌面截图与 3200×2136 那版逐项对比布局。

## 5. 什么时候做

| 前置 | 状态 |
| --- | --- |
| DPU 直扫（uke D1b/D2） | 17 线还没有（我们是 CPU 拷贝 + WC 映射）；27 线连显示驱动都没有 |
| GPU 合成器走 Metal | 17 线未完成（uke 在做） |
| 27 线显示 archive | 缺；但 ABI 材料已从 uke 拿到（见 `IPADOS27-MIGRATION.md` §6.19） |

所以：**不阻塞任何当前工作**，等 DPU 直扫落地后再作为一项独立优化做。在那之前，
把这份分析留着比提前动寄存器更有价值——`DPU-TASKS.md` 的风险清单第 1 条就是
"碰硬件前先出快照，抄固件现状，不猜寄存器"。
