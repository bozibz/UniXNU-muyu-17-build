## 3. 当前卡点的完整因果链

1. dyld 走的是「不滑动」的映射路径（`_shared_region_map_and_slide()` 里 `mappings_to_slide_cnt == 0`）；
2. 因此 `shared_region_pager` 的 `srp_slide_info == NULL`，页被**原样拷贝**；
3. 缓存页里的 threaded pointer 保持原始 `runtimeOffset`（如 `0x1a903070`、`0x4e4e8c5070`）；
4. 用户态一用它就跳进未映射区 → `EXC_BAD_ACCESS` / translation fault level 0（`esr=0x92000004`）→ launchd SIGSEGV（`namespace 2 subcode 0xb`）。

旁证：`0x180000000 + 0x1a903070 = 0x19a903070` 正好落在 `dyld_shared_cache_arm64e.07` 的映射区间内
⇒ 那个「坏指针」确实是缓存内偏移、只差一个基址。

## 9. u83–u84：入口点计数做出来了，pid 1 **两条路都走了**（2026-11-07 13:4x–14:1x）

### 9.1 先修「诊断行看不见」这件事（u83 的意外收获）

之前 u81/u82 的 `si=` / `sl_ent=` 读数其实**从来没有显示出来过**。实测：

- 面板上 `[owner …]` 行**总是在 `sl=0/0/` 处结束**，后面紧跟一个 `]`；
- u80（消息 252 字符）、u83（249 字符，消息前缀多了 111 字符的 `[u83 …]` 后总长 360 字符）
  结尾都是同一内容点 ⇒ **不是按长度截断，而是内容到那里就停了**；
- `sl=%llx/%llx/%llu/%llu/%llu` 里 `%llx` 两个值都印出来了（`sl=0/0/`），第三个是**第一个 `%llu`**；
  而 `sl` 之后的所有字段（`si` / `sl_ent` / `fs` / 新增字段）一个都没出现，
  且 `muyu_open_trace_format()` 的 ` n=…` 也没有被追加（说明 snprintf 返回值 ≥ 缓冲区长度）。

⇒ 结论：这个内核的 `snprintf()`（`bsd/kern/subr_prf.c` → `__doprnt`）在这一串参数上会在
**第一个 `%llu` 处停止输出**，并且返回「已写满」的长度。**不再用 `%llu` 写诊断**。
（`osfmk/kern/printf.c` 的 `_doprnt` 支持 `%llu`；问题只出在 bsd 的 `__doprnt` 路径上。）

**以后的规矩：诊断字符串只许用 `%u` / `%x` / `%llx`；重要数字放在 panic 文本最前面**
（u84 起在 panic 开头加 `[u85 …]` 前缀，已经验证能完整显示）。

### 9.3 离线核对这份缓存（挂着的 IPSW SystemOS 卷）

脚本：按 `dyld_cache_header` + `dyld_cache_mapping_and_slide_info`（每条 56 B）解 80 个文件：

- 80 个文件、**104 个 mapping**，范围 `0x180000000 … 0x2FD43C000`；
- `sharedRegionStart=0x180000000`、`sharedRegionSize=0x17d438000`、`maxSlide=0x20000000`、

⇒ 这份缓存的 rebase 信息**不是**老的 `slideInfoOffset` 大块，而是**逐 mapping 记在

### 9.7 找到新的头号嫌疑：4 KiB 页内核 + 16 KiB slide 页

`osfmk/vm/vm_shared_region_pager.c` 的 `shared_region_pager_data_request()`：

```c
slide_info_page_size = …si_slide_info_entry->page_size;       // 这份缓存 = 0x4000 (16 KiB)
for (offset_in_page = 0; offset_in_page < PAGE_SIZE; offset_in_page += slide_info_page_size)
        bcopy(src_vaddr + offset_in_page, dst_vaddr + offset_in_page, slide_info_page_size);
        … vm_shared_region_slide_page(…, offset_in_sliding_range / slide_info_page_size, …)
```

- 本内核 **PAGE_SIZE = 4096**，而 `slide_info_page_size = 16384` ⇒ 循环只跑一次，
  **`bcopy` 每次搬 16 KiB 写进一个 4 KiB 的目标页**，而且页索引用 4 KiB 偏移除以 16 KiB；
- 能正确处理「16 KiB slide 页 → 4 KiB 内核页」的 `shared_region_pager_slide_part()` 那条分支
  被 `#if !defined(APPLE_ARM64_ARCH_FAMILY) && !__ARM_16K_PG__` 关掉了（本内核定义了
  `APPLE_ARM64_ARCH_FAMILY`），正是 u79 发现的事实的另一面。

⇒ 这可以解释：映射存在（`ksl=15`）、页也能读，但**页内容没有被正确 rebase**（或写坏），
用户态拿到 chained 原值就跳飞。u86 正在直接量这条：`sr=<pager 请求数>,<slide_info_page_size>,<slid>/<slid_error>/<copied>`。

### 9.9 u86 读数：pager 真的在跑，而且**就在 16 KiB / 4 KiB 的错位上**

u86 = `fw/vendor_boot_27-u86.img` `738f24b5…`（内核 `9527321d…`）：

```
[u86 ml=1,1,1,r1,a101342000,z8000,o7c000,sl12c6000,ia1012c6000,e4
     s2=1,1,1,f79,m101,ns15,np15,sl20000000/1fa0000,sisf2e,ksl15,pg0/0
     sr=63,4000,3f/0/0 seq=f7b/6 …]
```

| 字段 | 值 | 含义 |
| --- | --- | --- |
| `sr=63,…` | **63 次** page-in 请求 | 共享区 pager **确实被调用**（不是没人用）|
| 第 2 项 | **0x4000** | `slide_info_page_size` = **16 KiB**，本内核 `PAGE_SIZE` = 4 KiB ⇒ **错位** |
| `3f/0/0` | slid 63 / slid_error 0 / copied 0 | 每次都走了 slide 分支，**没有报错**，所以「看起来成功、实际错」|

结合 9.7 的代码：`bcopy(..., 0x4000)` 往一个 4 KiB 目标页搬 16 KiB，并且
`offset_in_sliding_range / 0x4000` 的页号对第 2/3/4 个 4 KiB 分片是错的 ⇒
**同一条 16 KiB chain 只会被正确处理它自己那一段，其余分片读到的是原值**。
这正是「`far` 是 chained 原值、且每次都不同」的直接解释。

（u86 的 `sis f2e` / `ksl15` / `np15` 与 u85 完全一致，说明 dyld 侧的输入是稳定正确的。）

### 9.30 一个需要更正的技术判断

### 11.21 u99：抓 launchd 的退出原因（16:19:46 启动）

### 11.25 u101：抓“谁给 pid 1 发 SIGSEGV”（16:28:22 启动）

`fw/vendor_boot_27-u101.img` = `2f9d1149…`（内核 `f72549a1…`）。

`bsd/kern/kern_sig.c` 的 `psignal_internal()` 入口加钩子：`signum == SIGSEGV && pid == 1` 时
记下 `muyu_sig_num / muyu_sig_flavor`；前缀最前面变成
`ubt=<pc,lr,sp,fp,x0,x1> sig=<num>/<flavor> …`。

判读：

- `sig=11/0` ⇒ 从 `psignal()` 普通路径来的（多半是 **kill/raise/abort** 的用户态自杀）；

- `sig=0/0` ⇒ 连 `psignal_internal` 都没被调用，`initproc` 是因别的路径退出

—— 这一条能直接区分「launchd 被自己/别人杀死」和「launchd 主动 exit 但被记成 SIGSEGV」，
